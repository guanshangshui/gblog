## 一、引言：当提示词工程走到尽头

你有没有遇到过这样的情况：刚开始测试时，你的 Agent 表现得聪明伶俐，但一旦让它处理稍微长一点的任务，比如连续分析十几份文档，它就开始变得迟钝、逻辑混乱，甚至一本正经地胡说八道。这不是你一个人的困扰，这是几乎所有 Agent 开发者都会撞上的那堵看不见的墙。

我最近深入研究了 Anthropic、Cursor 和 OpenAI 这些行业领军者分享的 Agent 构建经验，发现了一个让人警醒的事实：过去三年里我们对提示词工程的过度依赖，已经走到了架构性破产的边缘。换句话说，当 Agent 从简单的聊天机器人进化到需要自主决策、长时间运行的复杂系统时，单纯靠优化提示词已经不够用了。

真正的分水岭在哪里？在上下文工程。正如 Anthropic 在他们的博客中直言不讳地指出：构建顶尖 Agent 的关键，不再是寻找那个完美的提示词，而是如何最高效地配置和管理上下文。这背后的逻辑很简单，你给模型看什么、怎么看、什么时候看，比你怎么问它更重要。

## 二、范式转变：为什么要抛弃微调，拥抱上下文工程

在传统的 AI 开发思路里，微调一个专属模型曾经被当作进入垂直领域的唯一门票。但这条路有个致命问题：太慢了。从收集数据、训练模型到验证效果，整个循环可能要花上几周时间。在今天这个业务需求瞬息万变的环境里，这种速度根本跟不上节奏。

Manus 团队的转型经验给了我们一个更聪明的思路。他们的工程师 Picu 在博客里用了一个很生动的比喻：如果把模型比作海面上涨的潮水，那么 Agent 应该是一艘船，而不是固定在海岸上的柱子。这意味着什么？意味着 Agent 应该与底层模型保持独立但紧密的关系，随着模型能力的提升而自然受益，而不是把自己的命运绑死在某个特定版本的模型上。

通过上下文工程，Manus 把改进迭代的周期从数周压缩到了数小时。这种思路的核心在于：与其花大力气去修改模型大脑里的神经回路，不如精妙地管理它能看到的每一个 token，每一条信息。换句话说，我们不是在改造模型的思维方式，而是在优化它的信息摄入和处理流程。

## 三、七个关键技巧：构建高效上下文的实战经验

### 技巧一：优化 KV 缓存命中率

#### 为什么缓存命中率是黄金指标

在生产环境中开发 Agent 时，有一个指标常常被忽视，但它实际上直接关系到你的钱包和系统性能，那就是 KV 缓存命中率。这不仅仅是用户体验和响应延迟的问题，更是实打实的成本问题。

让我给你看一组数字。以 Claude Sonnet 为例，使用缓存后的读取成本是每百万 token 0.3 美元,而标准输入则高达每百万 token 3 美元。这是 10 倍的差价。如果你的 Agent 每天处理大量请求，这个差距会在月底的账单上清晰地体现出来。更重要的是，缓存不仅能降低成本，还能显著提升计算速度，让你的 Agent 响应更快。


![[gblog/src/content/posts/_附件_/4d4d4c26b915f33126aac769a385f459_MD5.jpeg]]

#### 如何提升缓存命中率

那么问题来了，如何保持高效的 KV 缓存命中率？答案藏在一个很多人容易忽略的细节里：格式稳定性。

缓存的最大杀手是什么？是那些看似无害的动态内容。比如在系统提示词开头插入精确到秒的时间戳，或者使用键值顺序不确定的 JSON 序列化方式。这些做法会导致每次请求时，即使核心内容完全相同，提示词在字符串层面也会发生变化。服务端看到的是不同的输入，自然就无法命中缓存，必须重新推理整个上下文。

这背后的逻辑其实很直接：那些本应该保持不变的内容，比如系统提示词、工具定义、使用说明、沙箱环境配置，这些占据上下文大头的部分，如果能在客户端就确定下来并保持稳定，就能最大程度地保证前缀缓存有效。换句话说，不要让可以不变的东西发生改变。

具体怎么做？把动态信息和静态信息分离。时间戳、用户特定数据这些动态内容，放在提示词的后半部分。系统级的配置、工具定义这些静态内容，放在前面并保持格式固定。这样简单的调整，就能让你的缓存命中率从 20% 提升到 80% 以上。### 技巧二：警惕编造阈值

#### 现象：质量的断崖式下跌

这是一个让人困惑的现象：你让 Agent 分析 20 份 PDF 文档,前面几份它还认认真真地工作，但到了第八、第九份的时候，质量突然断崖式下跌。它开始敷衍，开始编造，甚至开始一本正经地胡说八道。这不是某个特定模型的问题，即使是 GPT-4 或 Claude 3.5 Sonnet 这样遵循指令能力最强的模型，也会遇到这个困境。

#### 原因：有效上下文的认知负荷

这背后的原因很反直觉。这不是模型记不住前面的内容，也不是上下文窗口不够用，而是有效上下文满了。当上下文长度压力超标时，模型遵循指令的能力会自然降低。更关键的是，大部分模型的训练数据都是较短的对话轨迹，所以当它们处理超长序列时，会本能地表现出一种急躁的风格，想要快速结束任务。

![[gblog/src/content/posts/_附件_/719adc60f92b1b3ce37dc19f464de152_MD5.jpeg]]

这种现象比普通的幻觉更可怕。因为它往往发生在任务进行到一半的时候，模型为了完成用户的要求，会从"根据提供的资料进行真实研究"切换到"基于概率的统计生成模式"。它生成的内容依然听起来很权威、很专业，但实际上大部分都是编造的。如果不经过严密的核查，你甚至很难发现问题。

当压力超过阈值时，模型会做出一个隐性的权衡：与其承认自己处理不了，不如用看起来合理的内容把任务完成。这就是为什么即使上下文窗口有 128K 甚至 100 万 token，Agent 依然会面临认知负荷和"迷失在中间"的困境。

#### 解决方案：多 Agent 协同架构

解决这个问题的经典思路是多 Agent 协同。让一个主 Agent 把握用户的核心需求，然后分派多个子 Agent 去完成细小的任务，比如阅读单个 PDF、搜索特定内容、总结段落。这样每个 Agent 的上下文压力都保持在安全范围内，就能避免触发编造阈值。当然，这涉及到更复杂的架构设计，不是本文的重点，但你需要知道这个现象的存在，才能理解为什么单 Agent 处理长任务时会失败。

### 技巧三：遮蔽而非移除工具

#### 问题：工具过多导致 Agent 变笨

当你的 Agent 接入了几十个工具，或者集成了各种 MCP 服务器后,你会发现一个奇怪的现象：Agent 变笨了。这既是因为过多的工具定义和描述占据了大量的 token 空间，也是因为工具数量增多后，很多工具的描述开始重叠、功能开始模糊，Agent 在选择时会变得犹豫不决。

直觉的解决方案是什么？动态移除无关的工具。比如当用户在做文件操作时，就把网络请求相关的工具从列表里删掉。听起来很合理，但这恰恰是灾难的开始。

还记得我们前面说的 KV 缓存吗？修改工具定义会导致缓存全部失效。更糟糕的是，这还会诱发幻觉。因为上下文通常会保留之前的对话历史，如果 Agent 在前面的步骤中调用了某个工具，但在下一轮推理时发现工具定义里找不到这个工具了，它就会陷入困惑，甚至开始编造工具的行为。


![[gblog/src/content/posts/_附件_/c2b45c51453fe5644ddddf841a4b70c1_MD5.jpeg]]

#### 优雅方案：逻辑遮蔽

Manus 提供了一个优雅的解决方案：逻辑遮蔽。核心思想是利用响应预填充技术，在不修改工具定义的前提下，提前约束 Agent 的动作空间。具体来说，就是通过强制预填充前缀来限制工具选择范围。比如预填充 "tool_name: browser_"，这样 Agent 就只能选择以 "browser_" 开头的工具，但工具定义本身没有任何改变，缓存依然有效。

这种命名规范的方式不仅优化了工具选择，还避免了昂贵的有状态 logits 处理器。在保持 KV 缓存稳定性的同时，以最低的成本降低了模型无效发散的可能。

#### 工具组织的最佳实践

另一个值得借鉴的实践是工具的组织方式。传统做法是把所有工具平铺在一个 JSON 数组里，但实践发现，如果把工具组织成树状结构，类似文件系统那样的层级关系，Agent 的效率会显著提升。比如把文件操作相关的工具放在 "file_system" 命名空间下，网络请求放在 "network" 下，这样 Agent 在选择工具时就有了更清晰的认知框架。

### 技巧四：文件系统作为外部记忆


#### 物理限制：注意力的 N 方复杂度

即使我们有 128K 甚至 100 万 token 的上下文窗口，也逃不开一个物理级别的限制：注意力机制的 N 方复杂度。上下文越长，模型处理每个 token 的计算成本就越高，而且质量还会下降。这就是为什么 Cursor 和 Manus 都推崇动态上下文的原因。

#### 核心思想：神经图灵机的现代实现

动态上下文的核心思想很简单：只披露最小量的必要上下文，后续需要的任何信息都由 Agent 自己通过检索来获得。这实际上是神经图灵机的一种现代实现，把文件系统当作外部记忆磁带。Agent 不需要把所有信息都塞进脑子里，而是学会在需要时去查阅外部存储。

![[gblog/src/content/posts/_附件_/b702559a50d3ad0d9a84ed704f83f659_MD5.jpeg]]



#### 实践效果：47% 的 Token 节省

Cursor 在他们的博客中提到，动态上下文发现的 token 使用效率远比用户手动填入的高得多。这背后有两个原因：动态加载的内容能够长时间保持在有效上下文中，因为它们是 Agent 主动请求的，相关性更高；同时，这种方式能减少上下文窗口过长导致的信息混淆和矛盾，从而提升回复质量。

Cursor 的 AB 测试表明，通过动态加载 MCP 工具和文件内容，token 消耗可以减少约 47%。这证明了将长期状态外部化，是绕过 Transformer 注意力衰减机制的有效策略。

#### 工程实践技巧

从工程实践角度，这里有几个具体的技巧。把每次命令的执行结果先外化到指定的临时文件中，而不是直接塞进上下文。当 Agent 需要相关信息时，可以直接用原生的搜索命令快速定位。这样既节省了上下文空间，又保留了完整的信息。

另一个场景是上下文压缩。当对话历史变长时，我们通常会对其进行压缩。但如何确保压缩后的内容足够优质？一个可行的思路是把压缩前的原始内容保存到文件中，然后把压缩后的摘要和文件路径一起提供给下一轮对话。如果新的 Agent 对上一轮的行动有疑问，可以直接查阅原始文件。这种方式能很大程度提高 Agent 的可靠性，因为它既有高层次的摘要，又能在需要时深入细节。

### 技巧五：保留错误历史

#### 开发者的通病：清理失败痕迹

开发者有一个通病：喜欢清理失败的痕迹。这很自然，因为直觉告诉我们，错误的内容会污染上下文，混淆 Agent 的判断。但在上下文工程的实践中，这个直觉是错的。

#### 为什么错误是宝贵的学习证据

抹除错误就等同于抹除 Agent 的学习证据。当 Agent 能在上下文中看到失败的尝试、异常报错、堆栈跟踪时，它实际上获得了宝贵的信息：哪些路径是死胡同。这会迫使它在下一次推理时探索新的解空间，而不是重复同样的错误。


![[gblog/src/content/posts/_附件_/167ef27f357bda28693cc207e40baff7_MD5.jpeg]]




实践证明，具备错误恢复能力的 Agent，其整体表现往往高于那些错误被清理过的 Agent。这背后的逻辑是，模型本质上是一个模式识别系统，它需要看到完整的因果链条才能做出更好的决策。如果你把失败的部分删掉，就相当于打断了这个链条，Agent 可能会在同一个地方反复摔倒。

#### 如何正确保留错误

当然，这不意味着要无限制地保留所有错误。关键是保留那些有信息价值的失败，比如尝试了某个 API 调用但返回了 404，或者执行了某个命令但权限不足。这些错误告诉 Agent 环境的约束和边界。而那些纯粹的格式错误或者重复的无效尝试，可以适当清理。

具体实践中，可以在上下文中保留最近的几次失败尝试，并在每次失败后添加简短的标注，说明为什么这个方案不可行。这样 Agent 在下一轮推理时，就能快速排除已知的死路，提高探索效率。

### 技巧六：定期复述任务目标


#### 待办事项的隐藏价值

如果你用过 Claude Code 或者 Manus，你会注意到一个有趣的功能：待办事项列表。当面对复杂任务时，这些 Agent 会先根据需求做详细分析，生成一份待办事项清单，然后在执行过程中不断更新这份清单，确保不会偏离目标。

#### 注意力操纵的精妙机制

这看起来像是一个简单的项目管理功能，但实际上是一种精妙的注意力操纵机制。通过不断重写任务列表，Agent 实际上是在把全局计划反复推回其短期注意力的有效范围内。这种利用自然语言进行的强制复述，能很大程度上解决"迷失在中间"的问题。

![[gblog/src/content/posts/_附件_/652974eb416f75823b35525d500a5607_MD5.jpeg]]




想象一下，如果没有这个机制会发生什么。Agent 在第 50 步、第 100 步的时候，可能已经完全忘记了最初的目标，开始在细节中迷失。但如果每隔几步就复述一次"我们要做什么，现在完成了哪些，还剩什么"，就能把它拉回正轨。

这背后的原理和人类的工作方式很像。当我们处理复杂项目时，也需要定期回顾目标和进度，否则很容易陷入细节而忘记大局。对于 Agent 来说，这种复述更加重要，因为它的"记忆"本质上是上下文窗口，而注意力会随着上下文变长而衰减。

#### 实践建议

实践中，你可以在系统提示词中明确要求 Agent 定期生成或更新任务清单。比如每完成 3-5 个步骤，就输出一次当前状态和剩余任务。这个简单的机制能显著提升长任务的完成质量。

### 技巧七：避免少样本陷阱

#### 模仿者的本质

少样本提示在提示词工程中是一种常见的技术，通过给模型展示几个示例来引导输出格式。但在 Agent 系统中，这个技术可能会以一种微妙的方式适得其反。

我们得承认一个事实：大语言模型本质上是一个优秀的模仿者。无论是零样本还是少样本，它们都会努力模仿上下文中的行为模式。问题在于，当这种模式没有被明确标记为错误时，模型会不自觉地重复它，即使这个模式并不是最优解。

#### 重复决策的危险

这在涉及重复决策的任务中特别危险。比如你让 Agent 帮你审查 20 份简历，它很可能会陷入一种节奏：因为在上下文中看到了前几份简历的处理方式，就机械地重复同样的结论。这会导致偏离、过度泛化，甚至产生类似幻觉的效果。

[[gblog/src/content/posts/_附件_/1e822f8e1fa11887142182b3094d3e7a_MD5.jpeg|Open: Pasted image 20260202200242.png]]
![[gblog/src/content/posts/_附件_/1e822f8e1fa11887142182b3094d3e7a_MD5.jpeg]]




如果你的上下文中充满了重复的动作、相似的观察结果，模型会不自觉地倾向于遵循这种方式，即使它并不适用于当前情况。这就像是一种隐性的过拟合，模型过度学习了上下文中的表面模式，而忽略了任务的实质差异。

#### 解决方案：引入多样性

解决方法其实很直接：增加多样性。在 Agent 的行动和观察记录中，引入少量的结构性变化。比如使用不同的序列化模板、调整措辞顺序、在格式上加入微小的噪音。这种人工控制的随机性有助于打破模型的惯性注意力，迫使它真正思考每个任务的独特性，而不是简单地复制粘贴之前的行为。

换句话说，不要让你的上下文变成一个单调的回音室。上下文越单一，Agent 就越脆弱，因为它缺乏真正的理解能力，只是在进行模式匹配。适度的多样性能让它保持警觉，对每个新任务做出更准确的判断。

## 四、结语：记忆空间决定智能边界

Agent 构建的未来，正在从单处理器顺序执行的模式，转向编排化并行架构。无论是以 Agent 调度 Agent 为核心的 Wide Research 架构，还是基于动态发现的上下文构建，都在告诉我们同一个事实：智能体的上限，往往取决于你如何塑造它的记忆空间。

我们已经走过了提示词工程的黄金时代。那个时代里，找到一个完美的提示词就能解决大部分问题。但现在，随着任务复杂度的提升和模型能力的增强，游戏规则变了。上下文工程成为了新的战场，它要求我们从系统架构的层面思考：如何让 Agent 看到它需要看到的，如何让它记住它应该记住的，如何让它在长时间运行中保持清醒和专注。

这七个技巧，从 KV 缓存优化到错误保留，从工具遮蔽到动态上下文，每一个都在解决同一个核心问题：如何在有限的注意力窗口内，最大化 Agent 的认知效率。它们不是孤立的技巧，而是一套完整的思维框架，帮助你构建真正稳健的 Agent 系统。

当上下文窗口不再是限制，当模型能力持续提升，真正的挑战就变成了：你的架构是否已经准备好迎接 AI Agent 时代的并行化浪潮？不要再过度纠结于提示词是否完美，去构建真正足够稳健的上下文状态基础设施。这才是通往高效 Agent 的真正道路。
