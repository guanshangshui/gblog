# 什么是 AI Agent：从对话模型到可行动的闭环系统

这篇作为系列的第一篇，我想把节奏放慢一点，先把一件最容易被忽略、却会影响后面所有讨论的事讲清楚：我们在说 agent 的时候，到底在说什么。

我写这一章有一个很现实的动机。只要有人开始讨论 agent，沟通成本往往会突然飙升，因为大家脑子里装着的“agent”根本不是同一个东西。常见的偏差大概分成两类：一种把 agent 神秘化、超级化，仿佛它天然就无所不能，什么复杂任务丢进去都能自己搞定；另一种把 agent 过度简化，觉得无非是把 ChatGPT 包一层壳，多调几次接口。前者会导致不切实际的期待，后者会导致错误的系统设计。两边都在用同一个词，却在讨论两种完全不同的系统形态。

要把这件事拉回地面，我们得先承认一个事实：能力的质变并不只来自模型“更聪明”了，也来自我们围绕模型搭出来的一套流程。换句话说，大模型的智力增长提供了上限，agent 的工程结构决定了你能不能把上限稳定地拿到手，甚至把它扩展到真实世界里。

---

## 先看清大模型本身擅长什么，也天然缺什么

如果把大模型拆到最底层，它本质上是在做一件非常朴素的事：给定已有的文本上下文，预测下一个 token 最可能是什么。你可以把它想成一个概率意义上的“文字接龙器”，只不过训练数据足够大、参数足够多，于是它能接出非常像样的答案，甚至看起来像在思考。

这带来一个很关键的后果：模型的“思考过程”在很多时候对我们是黑盒的。它并不真正理解现实世界正在发生什么，也无法直接接触现实世界本身。它更像是把训练时见过的大量模式，在当前输入里重新激活，然后沿着概率最高的路径往下生成。

模型的知识通常来自两类来源。第一类是预训练沉淀下来的世界知识，也就是模型厂商在训练时喂进去的文本和结构化数据在参数里形成的隐性记忆。你问到它见过、学过的东西，它就能“从脑子里”拿出来讲得头头是道。第二类是你当下提供的上下文，比如提示词、上传的资料、对话历史，这些都会改变它接下来要生成的 token 分布。

问题在于，当我们用网页对话的方式去做真实任务时，人类能提供的上下文往往非常有限。很多真实世界的问题，关键信息根本不在你的提示词里，而是分散在系统状态、文件内容、网页信息、数据库记录、传感器读数、外部接口返回值这些地方。你很难把这些完整而准确地“复制粘贴”给模型。于是就会出现一种典型困境：模型看起来很会说，但它缺少真实的外部证据来校准自己，于是幻觉和拍脑袋就变得难以避免。

这也是 agent 出场的原因。

---

## Agent 的能力质变，来自一个朴素但强力的闭环

当我们说 agent 的时候，我更倾向于把它理解为一个“带行动能力的闭环系统”，而不只是一个会聊天的模型。它的关键不在于某个神秘的模块，而在于一个非常工程化的循环过程，也就是常说的 agent loop：

模型先基于当前目标与上下文进行推理和计划，然后采取行动去影响外部世界，接着读取行动带来的结果，把结果作为新的上下文，再继续推理和修正计划。思考，行动，观察，再思考。循环往复，直到任务完成或触发停止条件。

这个循环为什么能带来质变？因为它把一次性生成答案的行为，改造成了逐步获取证据、逐步减少不确定性的过程。单次对话里模型很多时候在“猜”，猜用户想要什么，猜事实是什么，猜哪条路径会成功。进入闭环之后，它可以先做一个小动作去探路，再把真实反馈拿回来校准自己，然后继续走下一步。

你会发现，很多现实任务本来就不适合一口气生成答案。它们更像是一个人在陌生环境里做事：先看一眼现状，做一步试探性的操作，观察结果，修正判断，再继续推进。agent loop 把这种“与世界互动中逐步逼近正确解”的能力，交给了大模型。

---

## 观察与执行，才是 Agent 连接现实的接口

闭环要成立，核心就落在两类能力上：观察外界，执行动作。

观察这件事，你可以把它理解为传感器。传感器不一定是物理的摄像头、麦克风、雷达，也可以是软件意义上的读取渠道，比如命令行输出、文件内容、网页抓取结果、数据库查询返回、某个 API 的响应。它们的共同点是把外界状态变成模型能读懂的文本或结构化信息，注入到下一轮上下文里，让模型不再只靠“世界知识的记忆”去做推断，而是能基于“眼前正在发生的事实”去更新判断。

执行这件事，你可以把它理解为执行器。执行器同样既可以是物理设备，比如机械臂、方向盘，也可以是虚拟工具，比如运行一段 Python 脚本、调用一个接口、修改一个配置、提交一次代码变更。执行器的意义在于，模型不再只能给建议，它能对环境施加影响，让任务真正往前走。

当观察和执行被接入，循环就闭上了。模型做决定，执行器把决定落到现实里，传感器把现实的反馈带回来，再影响下一轮决定。这个结构看起来简单，却非常接近许多真实智能系统的本质。

---

## “思考”这一环，决定了闭环的质量

很多人第一次做 agent，会把注意力全放在工具调用上，觉得能调用 API 就是 agent。实际上，工具只是手脚，思考方式决定了你是在乱挥拳，还是在有计划地解决问题。

这里我想引入一个很重要的脉络，也就是结构化推理的思想。早期大家通过提示词要求模型“把推理过程写出来”，后来出现了思维链相关的研究与工程实践，进一步验证了一个现象：当你强制模型把复杂任务拆解成更小的步骤，并且让每一步都依赖前一步的结果时，复杂任务的成功率往往会上升，模型的跳步、拍脑袋会减少，错误也更容易在中途被发现并纠正。

从工程角度看，这里真正有价值的点并不在于写出一段漂亮的推理文字，而在于把任务变成可迭代的决策序列。闭环的优势只有在“每一轮都有明确意图”时才会出现，否则循环只是在反复生成。

---

## 经典定义与现代 LLM agent，其实能对上号

agent 这个词并不是大模型时代才出现的。更经典的定义通常是：任何能够通过传感器感知环境，并能通过执行器对环境采取行动，以达成特定目标的实体，都可以被称为 agent。

你会发现，这个定义天然包含几个要素。它有一个外部环境，环境对它来说是动态的、可被感知的。它需要感知渠道把环境状态带回来。它也需要行动渠道把自己的决策施加出去。最后，它要有一个目标导向的决策机制，让行为具备方向感，而不是随机游走。

当我们把这个定义映射到今天的大模型系统里，很多东西就变清楚了。像 Claude Code 这类编程 agent，它的环境更接近你的本地系统与代码仓库。自动驾驶系统的环境是道路交通的连续变化。交易算法的环境是金融市场的实时波动。它们的共同点从来不是“会说话”，而是“能在反馈中持续调整策略”。

---

## 一个更贴近直觉的比喻：从口算天才，到会做实验的学霸

如果用一个比喻来收尾，我更愿意把大模型看成一个天赋极高、反应很快的学生。

最早的网页对话形态，有点像这个学生只用心算口算，一口气把答案报出来。看起来很自信，也经常能答对，但你很难知道它怎么得到的，遇到信息不足的题就容易猜错。

后来大家引入结构化推理，更像是要求他把草稿写出来，把复杂题拆开一步步算。稳定性提升了，因为错误更容易暴露，推理也更不容易跳步。

而 agent 进一步把他从“只会在脑子里想”升级成“会去做实验、会去查资料、会去动手验证”。他遇到不确定的信息，会先去读取文件、跑个脚本、查个接口，用真实反馈来修正自己的判断，再继续推进。能力的增长点就在这里：从单次生成，变成与环境互动的闭环求解。

---

## 小结

写到这里，我们已经把“什么是 agent”这件事落到了一个可以对齐共识的框架里：agent 的关键在于闭环，在于思考，行动，观察的循环，在于传感器与执行器把模型接入真实环境，在于结构化决策让每一轮行动都带着明确目的。模型更聪明当然重要，但流程让聪明变得可用、可控、可验证。
